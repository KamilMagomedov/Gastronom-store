# Gastronom Backend

Backend для сервиса доставки продуктов питания (гастроном/продуктовый магазин). Построен на Laravel 12.

## Функциональность

### API (Mobile/Frontend)

- **Аутентификация** — регистрация, логин, OTP-верификация, восстановление пароля
- **Каталог** — товары, категории, поиск с фильтрацией, популярные товары
- **Корзина** — добавление/удаление товаров, хранение для гостей и авторизованных
- **Заказы** — создание, отмена, повтор заказа, история
- **Отзывы** — оценка и отзывы на товары
- **Профиль** — управление данными и адресами доставки
- **Проверка остатков** — эндпоинт доступности товара с опциональной проверкой нужного количества

### Онлайн-оплата (эквайринг с редиректом на банк)

Система построена на абстрактной архитектуре эквайеров: каждый банк — отдельный `Acquirer` в БД со своим JSON-конфигом (API-ключи). Клиент редиректится напрямую на страницу оплаты своего банка — без комиссий и посредников.

**Поддерживаемые банки:**

| Банк | code | Описание |
|---|---|---|
| Сбербанк | `sberbank` | SberPay, карты |
| Тинькофф | `tinkoff` | Tinkoff Pay, карты |
| ВТБ | `vtb` | ВТБ Онлайн, карты |
| Альфа-Банк | `alfa` | Альфа-Клик, карты |
| ПСБ | `psb` | ПСБ Онлайн, карты |
| Газпромбанк | `gazprom` | Газпромбанк Онлайн, карты |
| Наличными | — | Оплата при получении (без эквайера) |

**Flow оплаты:**
1. Клиент создаёт заказ → если выбран онлайн-способ, автоматически генерируется `payment_url`
2. Клиент переходит по ссылке на платёжную страницу своего банка
3. Банк присылает webhook на `POST /api/payments/webhook` → статус заказа обновляется
4. Клиент может явно запросить ссылку: `POST /api/v1/payments/{order}/initiate`

**Параметры инициализации:**
```json
POST /api/v1/payments/{order}/initiate
{
    "payment_method_type": "bank_card"
}
```

**Ответ:**
```json
{
    "success": true,
    "data": {
        "payment_url": "https://online.sberbank.ru/...",
        "transaction_id": 1,
        "acquirer": {
            "id": 1,
            "name": "Сбербанк",
            "code": "sberbank"
        }
    }
}
```

### Уведомления

- **OrderCreatedNotification** — email клиенту при создании заказа: состав, сумма, адрес доставки
- Уведомления отправляются через очередь (`ShouldQueue`)

### Архитектура платежей (новая)

Система переведена с YooKassa на абстрактную архитектуру банковского эквайринга.
Каждый банк — запись в таблице `acquirers` с полем `config` (JSON), где хранятся API-ключи.
Шлюз резолвится динамически по `code` эквайера через `Acquirer::gateway()`.

```
app/Services/Payment/
├── Contracts/
│   └── PaymentGateway.php              # Интерфейс платежного шлюза
├── Gateways/
│   ├── BaseAcquirerGateway.php         # Абстрактный базовый класс (HTTP, webhook, статусы)
│   ├── SberbankGateway.php             # Сбербанк (SberPay)
│   ├── TinkoffGateway.php              # Тинькофф (Tinkoff Pay)
│   ├── VtbGateway.php                  # ВТБ
│   ├── AlfaGateway.php                 # Альфа-Банк
│   ├── PsbGateway.php                  # ПСБ
│   └── GazpromGateway.php              # Газпромбанк
├── Exceptions/
│   └── PaymentException.php            # Исключение
└── PaymentManager.php                  # Менеджер: resolve() + gatewayForPaymentMethod()
```

**Новые сущности:**
- `app/Models/Acquirer.php` — модель эквайера с методом `gateway()`, резолвящим класс шлюза по `code`
- `database/factories/AcquirerFactory.php` — фабрика с состояниями для всех 6 банков
- `database/seeders/AcquirerSeeder.php` — сидер со всеми банками и env-плейсхолдерами
- `app/Filament/Resources/AcquirerResource/` — CRUD для управления эквайерами через Filament

**Добавление нового банка:**
1. Создать класс шлюза в `app/Services/Payment/Gateways/`, унаследовать `BaseAcquirerGateway`
2. Реализовать `initiatePayment()`, `processWebhook()`, `getPaymentStatus()`
3. Добавить код в `PaymentGateway` enum
4. Создать запись `Acquirer` в БД с нужным `code`
5. Добавить переводы в `lang/{ru,en}/payment.php`

## Настройка онлайн-оплаты

### 1. Переменные окружения

В `.env` добавить API-ключи для нужных банков:

```env
# Сбербанк
SBER_MERCHANT_ID=
SBER_LOGIN=
SBER_PASSWORD=

# Тинькофф
TINKOFF_TERMINAL_KEY=
TINKOFF_SECRET_KEY=
TINKOFF_TERMINAL_PASSWORD=

# ВТБ
VTB_MERCHANT_ID=
VTB_API_KEY=

# Альфа-Банк
ALFA_MERCHANT_ID=
ALFA_API_KEY=

# ПСБ
PSB_MERCHANT_ID=
PSB_SECRET_KEY=

# Газпромбанк
GAZPROM_MERCHANT_ID=
GAZPROM_API_KEY=
```

### 2. Миграции и сиды

```bash
php artisan migrate
php artisan db:seed --class=AcquirerSeeder
```

Сидер создаст записи для всех 6 банков. Неактивные можно отключить в админке.

### 3. Админ-панель (Filament)

**Управление эквайерами** — `/admin/acquirers` (`AcquirerResource`):
- Включить/отключить банк (`is_active`)
- Задать порядок сортировки (`sort_order`)
- Заполнить конфиг (API-ключи) для каждого активного банка
- Просмотреть список всех банков

**Способы оплаты** — `/admin/payment-methods` (`PaymentMethodResource`):
- Для каждого онлайн-способа оплаты выбрать эквайер из выпадающего списка (`acquirer_id`)
- Один эквайер можно привязать к нескольким способам оплаты (например, «Карта онлайн» и «СБП» к одному банку)

### 4. Что требуется от мобильного приложения

| Элемент | Что нужно сделать |
|---|---|
| Редирект после заказа | После успешного создания заказа перенаправить пользователя на `payment_url` из ответа API (это ссылка на страницу оплаты банка) |
| Кнопка «Оплатить» | Вызвать `POST /api/v1/payments/{order}/initiate` и открыть полученный `payment_url` |
| Вебвью для оплаты | Открыть `payment_url` во встроенном веб-вью (WebView). Банк сам покажет страницу оплаты. После оплаты — закройте веб-вью и обновите статус заказа через API |
| Статус оплаты | После закрытия веб-вью показать пользователю статус: обновить заказ через `GET /api/v1/orders/{order}` |
| Выбор банка | (Опционально) Показать список доступных эквайеров из `GET /api/v1/settings` → `data.payment_methods[].acquirer` |

Без этих доработок оплата будет создаваться на бэке, но пользователь не сможет на неё перейти и завершить.

**Важно:** Комиссия за транзакцию отсутствует — клиент платит ровно сумму заказа. Все банковские комиссии несёт магазин.

- Заменить заглушки в каждом `*Gateway.php` на реальные HTTP-запросы к API банка
- Протестировать flow оплаты и webhook-уведомлений
- Настроить обработку ошибок и таймаутов для каждого банка

## Проверка остатков товаров

Эндпоинт для проверки актуального наличия товара в реальном времени:

```
GET /api/v1/products/{slug}/availability
```

**Без параметров:**
```json
{
    "success": true,
    "data": {
        "product_id": 1,
        "slug": "milk-3-2",
        "name": "Молоко 3.2%",
        "in_stock": true,
        "stock_quantity": 42,
        "is_active": true,
        "available": true
    }
}
```

**С проверкой нужного количества (`?quantity=N`):**
```
GET /api/v1/products/milk-3-2/availability?quantity=10
```
```json
{
    "data": {
        "product_id": 1,
        "slug": "milk-3-2",
        "name": "Молоко 3.2%",
        "in_stock": true,
        "stock_quantity": 42,
        "is_active": true,
        "available": true,
        "requested_quantity": 10,
        "is_enough": true,
        "shortage": 0,
        "status": "available"
    }
}
```

Если товара не хватает:
```json
{
    "data": {
        "stock_quantity": 2,
        "requested_quantity": 10,
        "is_enough": false,
        "shortage": 8,
        "status": "out_of_stock"
    }
}
```

Поля:
| Поле | Тип | Описание |
|---|---|---|
| `in_stock` | bool | Заведён ли товар на склад |
| `stock_quantity` | int | Текущий остаток |
| `is_active` | bool | Активен ли товар |
| `available` | bool | Можно ли купить (активен + есть на складе) |
| `requested_quantity` | int | *Только если передан `?quantity=`* |
| `is_enough` | bool | Хватает ли остатка на запрошенное количество |
| `shortage` | int | Сколько не хватает (0 если хватает) |
| `status` | string | `available` / `out_of_stock` / `inactive` |

### Что требуется от мобильного приложения

| Элемент | Что нужно сделать |
|---|---|
| Проверка перед добавлением в корзину | При нажатии «Добавить в корзину» вызвать `GET /products/{slug}/availability?quantity=1`. Если `is_enough: false` или `available: false` — показать сообщение «Товара нет в наличии» |
| Проверка при изменении количества | При изменении количества в корзине дёрнуть эндпоинт с актуальным `quantity`. Если `is_enough: false` — показать предупреждение «Доступно только N шт.» |
| Блокировка кнопки «Оформить заказ» | Перед отправкой заказа проверить все позиции корзины на доступность. Если хотя бы одна позиция недоступна — показать список проблемных товаров и не дать оформить заказ |

### Валидация остатков при создании заказа (серверная)

При попытке создать заказ через `POST /api/v1/orders` бэкенд проверяет `stock_quantity` для каждого товара в корзине. Если хотя бы одного товара не хватает — заказ **не создаётся**, возвращается ошибка:

```json
{
    "success": false,
    "message": "Недостаточно товара на складе",
    "data": {
        "insufficient_items": [
            {
                "product_id": 1,
                "product_name": "Молоко 3.2%",
                "requested": 5,
                "available": 2
            }
        ]
    }
}
```

Статус: `422 Unprocessable Entity`. Заказ не создаётся, деньги не списываются, остатки не резервируются.

#### Фронтенд: обработка ошибки при создании заказа

| Элемент | Что нужно сделать |
|---|---|
| Обработка 422 при создании заказа | При получении `success: false` с `insufficient_items` — **не перенаправлять на оплату**, а показать пользователю список товаров, которых не хватает. Кнопка «Оформить заказ» должна оставаться нажатой/доступной, но заказ не создан |
| Отображение предупреждения | Показать модальное окно или блок с сообщением: «Недостаточно товара на складе» и перечислить проблемные позиции (сколько запрошено, сколько доступно) |
| Предложить действия | Дать пользователю варианты: убрать проблемные товары из корзины, уменьшить количество или отложить заказ |
